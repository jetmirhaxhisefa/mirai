# Unit 30: what the pilot found in MIRAI

Jet, 2026-11-16: "record this MIRAI gaps to be fixed later after the pilot. Meaning what we find
in pilot like problems we need to record to fix them."

Every problem MIRAI shows on the pilot goes here as it happens, with what we did instead. None is
fixed during the pilot unless it blocks it. After the pilot each one becomes a fix, a row or an
addition to a unit's spec, and its line here says where it went.

| # | Found | What happened | Workaround on the pilot | Fix after the pilot |
|---|---|---|---|---|
| F1 | 2026-11-16, keys | `mirai key new --machine` can't publish an existing machine key into a second repo: it refuses with "a machine key already exists on this machine". `mirai key new` (your key) does publish an existing key. | Copied the public file `k-6ffd6a59990e793c.machine.pub` from the sample app (`f39ba2a` on `mirai/pilot`). | `key new --machine` writes the existing machine key's public file, as `key new` does. |
| F2 | 2026-11-16, keys | F1's error hint suggests `mirai key new --machine --replace`. Following it would make a new machine key, and every other repo's records signed with the old one stop verifying until its new public file is published there. | Not followed. | The hint names the publish path from F1; `--replace` warns that the other repos need the new file. |
| F3 | 2026-11-16, setup | Thudos's Docker setup didn't fit MIRAI's test runs, and nothing said so before trying: compose used `env_file:` (refused by the strict text check), the frontend ran `npm install` at start (test runs have no network), the PHP image had no Composer packages baked in. Found by reading the sample app, not by MIRAI. | Changed the pilot's Docker files to the sample app's pattern (`9daed7c`). | `mirai detect` names each of these with the fix: `env_file` in a service, an install command in a `command`/`CMD`, a Dockerfile that doesn't install from the lockfile. Check what 17a already reports first. |
| F4 | 2026-11-16, install | After `mirai init`, the "Next" list says `mirai key new` and nothing about the machine key, which the install needs for the red team, baseline and proofs (29b). | Done by hand (F1). | `init`'s Next list names both keys, or one command publishes both. |
| F5 | 2026-11-16, install | Running MIRAI needs the full path (`node ~/Projects/mirai/bin/launch.js …`); `mirai` alone isn't a command. Jet: "very important that MIRAI gets installed with a command". | Full path in every instruction. | Roadmap row 12c. |
| F6 | 2026-11-16, detect | `mirai detect` found lint, build and format, but not the type check: Thudos's own gate (`scripts/quality-gate.local.sh`) runs `npx tsc -p tsconfig.app.json --noEmit`, and there's no `typecheck` script in `package.json`. 17a's spec says named checks come "from manifests' scripts and dependencies" and design/03 says "from the gate script". | Added `types` by hand (`c3377e9`). | Detection reads the project's gate script too, or drafts `types` when `typescript` and a `tsconfig*.json` are there. |
| F7 | 2026-11-16, detect | Detect drafted a `coverage`-capable Vitest level and a Playwright level without saying either can't work: no `@vitest/coverage-v8` in `package.json`, and the Playwright level runs in the `frontend` service, whose image has no browsers. | Playwright left out; Vitest without `coverage_paths`. | Detect names what each adapter needs and is missing (the coverage package; a browser image for Playwright). |
| F8 | 2026-11-16, baseline | `mirai detect` passed Thudos's compose file, then the first `mirai baseline` refused every level and check: `network hr-platform: driver, which test runs don't allow`. Detect also didn't warn that services built without an `image:` name can't be found by test runs (they never build, and use their own project name). The baseline exits 0 with INCOMPLETE. | Dropped `driver: bridge`, named both built images (`hr-platform/app:dev`, `hr-platform/frontend:dev`), rebuilt. | Detect runs the same tightening check as test runs and lists every refusal, with the fix, before a baseline is tried; and flags a built service with no `image:`. |
| F9 | 2026-11-16, baseline | A test that reads a committed, secret-free `.env.example` (`EnvExampleTest`, `env-drift.test.ts`) fails only in MIRAI's test copy, which leaves out every unlisted `.env*` file. The baseline then records it as a NEW known failure ("something broke on mirai/pilot"), which reads like a project bug. | Listed both `.env.example` files in `[sandbox] readable_env` (`58e52fb`). | Detect drafts `readable_env` from committed `.env*` files with no secret shapes (`.env.example`, `.env.testing`), for you to confirm; a failing test that opens a left-out `.env*` file is named as such in the baseline. |
| F10 | 2026-11-16, baseline | The Vitest adapter always adds `--coverage.*` in a baseline. Without `@vitest/coverage-v8` installed, Vitest stops before writing its JUnit report, so the whole level is `env-fault (bad-report)` and the baseline INCOMPLETE: no level result at all, not just no coverage. | Pending Jet's decision (add the package by hand, or run without coverage). | A level whose coverage package is missing runs without coverage and says so; or detect/doctor names the missing package before a baseline. |
| F11 | 2026-11-16, doctor | With the session server registered for an older trust root (`c3377e9`, four pushed commits behind), `mirai doctor` said "not registered for this project" (state `missing`), not "behind". Confirmed: after `session-server install` it reads "registered for the current trust root". | Re-ran `session-server install`. | Doctor says the server is registered for an older commit, and why that matters (`behind`). |
